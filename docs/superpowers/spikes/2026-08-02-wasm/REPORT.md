# WASM feasibility spike: screamer C++ kernels to JavaScript via Embind

Date: 2026-08-02. Toolchain: emcc 4.0.21, node v24.1.0, bundled wasm-opt.

## Verdict

Feasible, qualified. The real screamer kernel `screamer::detail::RollingMean`
compiled to WASM unmodified, ran under Node, and produced numbers that match
Python `screamer.RollingMean(3)` to the last bit, including NaN warmup, NaN
passthrough, and the post-NaN window recovery. All three feature mappings that
matter (data types, polymorphic dispatch, lazy plus async streaming) work in
JS with less glue than the Python side needed. The one real blocker is not
WASM: it is that screamer's public operator headers include nanobind through
`ScreamerBase`/`FunctorBase`, so today an operator header cannot compile
without CPython present. The spike sidestepped this by wrapping the
binding-free `detail/` kernel directly. A production binding needs the
base-class split so operator headers compile with no nanobind, plus an Embind
dispatch layer parallel to the nanobind one. Binary size is not a blocker:
one op is ~12.7 KB wasm after tuning, and each added operator costs a few
hundred bytes.

This spike wraps the REAL kernel. No rolling-mean or rolling-sum logic is
written in C++ or JS anywhere in these files; every number comes from the
kernel's own `append()`.

## Files

- `spike.cpp` - Embind wrapper over the real `screamer::detail::RollingMean`
  (persistent scalar object with `append`/`reset`, plus a heap-buffer batch
  path) and, under `-DSPIKE_MULTI`, a second distinct kernel `RollingSum` and
  two thin distinct subclasses for the marginal-cost measurement.
- `build.sh` - exact emcc commands and the size-measurement variants.
- `driver.mjs` - the JS driver: polymorphic wrapper, lazy and async
  generators, scalar and batch demos, the Python cross-check.
- `screamer_spike.mjs` + `screamer_spike.wasm` - build artifacts (the runnable
  module, `-DSPIKE_MULTI -Oz`). Regenerate with `build.sh`.
- `build/` - size-variant artifacts, also regenerated by `build.sh`.

Run: `bash docs/superpowers/spikes/2026-08-02-wasm/build.sh` then
`node docs/superpowers/spikes/2026-08-02-wasm/driver.mjs`.

## Q1. Compile

Proven. The kernel `detail/rolling_mean.h` and its two includes
(`common/float_info.h`, `detail/start_policy.h`) compile to WASM under
`emcc -I include` with no source change. The header's only non-header
dependency is `parse_start_policy()`, defined in the pure C++
`src/screamer/detail/start_policy.cpp`, which we compile alongside `spike.cpp`.
No reimplementation.

The `detail/` kernel is binding-free: a grep for nanobind across the three
headers finds nothing, and the compile succeeding with no CPython in the
sysroot confirms it. This is the crux of feasibility. Contrast the public
header `include/screamer/rolling_mean.h`, which includes
`screamer/common/base.h`, which includes `<nanobind/nanobind.h>`. That header
cannot compile under emcc without CPython. See the closing engineering section.

Toolchain issues resolved:

- Standalone `wasm-opt` rejected the emcc output with
  "memory.copy operations require bulk memory operations". emcc emits
  bulk-memory and nontrapping-float-to-int, which a standalone `wasm-opt` must
  be told to allow. Fix: pass `--all-features`. emcc's own internal `wasm-opt`
  pass already enables them, so only the extra standalone pass needed the flag.

## Q2. Data types

Proven, both a copy path and a zero-copy path.

Scalar. A JS `number` crosses to C++ `double`, through `append()`, and back to
a JS `number`:

```js
const s = new mod.RollingMean(3, 'strict');
const scalarOut = [1, 2, 3, 4, 5, NaN, 7].map((x) => s.append(x));
// scalar per-event : [NaN, NaN, 2, 3, 4, NaN, 5.333333333333333]
```

NaN survives the boundary intact in both directions (IEEE754 double).

Batch. A JS `Float64Array` goes in, a `Float64Array` comes out, with the loop
running in C++:

```js
const inPtr = mod.allocF64(n);          // malloc on the WASM heap
mod.viewF64(inPtr, n).set(arr);         // write via a typed_memory_view
const outPtr = mod.rollingMeanBatchInto(inPtr, n, size, policy); // malloc's out
const out = Float64Array.from(mod.viewF64(outPtr, n)); // copy out of the heap
mod.freeBuf(inPtr); mod.freeBuf(outPtr); // release both: no leak
// batch (copied)   : [NaN, NaN, 2, 3, 4, NaN, 5.333333333333333]
```

Memory ownership is the WASM analogue of nanobind's owner-capsule. The C++
`rollingMeanBatchInto` allocates the output with `malloc` and returns the raw
pointer; JS reads it, copies out, and calls `freeBuf`. Ownership is explicit
and single-owner. No leak (every `malloc` is paired with a `freeBuf`) and no
use-after-free (JS copies before freeing).

Near-zero-copy path. `emscripten::typed_memory_view(n, ptr)` returns a
`Float64Array` that aliases the WASM heap with no copy:

```js
const zc = batchRollingMean(input, 3, 'strict', { zeroCopy: true });
// zc.view aliases the heap directly
zc.free();                              // caller frees when done
// batch (zero-copy): [NaN, NaN, 2, 3, 4, NaN, 5.333333333333333]
```

Tradeoff, and it is real: the view is only valid until the buffer is freed or
the heap grows. With `-sALLOW_MEMORY_GROWTH=1`, any later allocation can detach
the backing `ArrayBuffer` and leave the view pointing at freed or moved memory.
So the zero-copy view must be consumed before the next allocation, and any view
captured across an `allocF64`/malloc call is stale. The safe default is the
copy path; reach for the view only in a hot loop that consumes immediately. The
driver also re-fetches a fresh `viewF64` after every alloc for exactly this
reason, rather than caching `HEAPF64`.

## Q3. Polymorphic interface

Proven. One callable from a `rollingMean(size)` factory dispatches on input
type, mirroring screamer's Python `Op(config)(data)`:

```js
function rollingMean(size, policy = 'strict') {
  const scalarOp = new mod.RollingMean(size, policy); // persistent stream state
  const fn = (data) => {
    if (typeof data === 'number') return scalarOp.append(data);       // scalar
    if (data instanceof Float64Array || Array.isArray(data))
      return batchRollingMean(data, size, policy);                    // batch
    if (data?.[Symbol.iterator]) return lazyRollingMean(data, size, policy); // lazy
    throw new TypeError('unsupported input');
  };
  fn.dispose = () => scalarOp.delete();
  return fn;
}
```

The same callable handling all three input kinds:

```
number  1 -> NaN
number  2 -> NaN
number  3 -> 2   (persistent stream state advances)
Array     -> [NaN, NaN, 2, 3, 4]
Float64Ar -> [NaN, NaN, 20, 30]
iterable  -> [NaN, NaN, 2, 3, 4]   (lazy generator)   // driven by a JS Set
```

`number` advances a persistent stateful WASM object; `Array`/`Float64Array`
run the batch path; any other iterable (a `Set` here, distinguished by having
`Symbol.iterator` but not being an array) returns a lazy generator.

## Q4. Lazy and async streaming

Proven, both sync and async.

Sync. A generator pulls one value at a time from an iterable and drives a
persistent WASM object per event:

```js
function* lazyRollingMean(iterable, size, policy = 'strict') {
  const op = new mod.RollingMean(size, policy);
  try { for (const x of iterable) yield op.append(x); }
  finally { op.delete(); }
}
// sync generator   : [NaN, NaN, 2, 3, 4, NaN, 5.333333333333333]
```

Async. An async generator consumes an async iterable with native
`for await...of`, one awaited event at a time:

```js
async function* lazyRollingMeanAsync(asyncIterable, size, policy = 'strict') {
  const op = new mod.RollingMean(size, policy);
  try { for await (const x of asyncIterable) yield op.append(x); }
  finally { op.delete(); }
}
// async generator  : [NaN, NaN, 2, 3, 4, NaN, 5.333333333333333]
```

The async source awaits a promise between events to simulate I/O. This is the
notable ergonomic win over Python: JS's async iteration is native, so a
streaming async op needs no coroutine bridge. The Python side reached for
`py::exec`-style plumbing to interleave a coroutine with the C++ op; on the JS
side the WASM object is just a plain stateful object that `for await...of`
drives directly. The persistent object outlives many `append()` calls and is
freed in `finally`.

## Q5. Correctness

Proven, exact match. Cross-checked against the actual Python
`screamer.RollingMean(3)` (screamer 2.0.0 is importable in the repo venv):

```
Python : [nan, nan, 2.0, 3.0, 4.0, nan, 5.333333333333333]
WASM batch : [NaN, NaN, 2, 3, 4, NaN, 5.333333333333333]
match (batch, scalar, lazy, async all == Python): true
```

Input `[1, 2, 3, 4, 5, NaN, 7]`, strict policy. Two things the kernel decides,
not the harness:

- Index 5 (NaN input) returns NaN and leaves state unchanged (the ignore
  policy in `float_info.h`/`rolling_mean.h`).
- Index 6 is 5.333..., not NaN. Because the NaN at index 5 was skipped, the
  window of the last three valid values is `(4 + 5 + 7) / 3 = 16/3`. The task
  brief flagged this as an assumption to verify against the kernel rather than
  guess; the kernel's answer is 5.333..., and the WASM output reproduces it.

All four JS paths (batch, per-event scalar, sync generator, async generator)
equal the Python reference element for element, NaN for NaN.

## Q6. Binary size

`.wasm` sizes, one operator (RollingMean alone), real bytes:

| build                         | raw wasm | gzip -9 |
|-------------------------------|---------:|--------:|
| `-O2`                         |   18,481 |   8,467 |
| `-Oz`                         |   17,459 |   7,944 |
| `-Oz` + standalone `wasm-opt` |   17,455 |   7,885 |
| `-Oz` + `-sMALLOC=emmalloc`   |   12,680 |   6,047 |

Smallest wasm: 12,680 bytes raw, 6,047 gzipped, with `-Oz` plus `emmalloc`.
The standalone `wasm-opt -Oz` pass on top of emcc's own barely moves the needle
(4 bytes) because `-Oz` already runs wasm-opt internally. The real lever on the
wasm is the allocator: default dlmalloc is heavy, and `emmalloc` cuts ~27% off
the baseline.

The JS glue is a separate, roughly fixed cost:

| glue build          | raw mjs | gzip -9 |
|---------------------|--------:|--------:|
| `-Oz` (default)     |  43,530 |  11,554 |
| `-Oz` `--closure=1` |  18,104 |   7,544 |

Closure compiler cuts the JS glue by more than half. A tuned single-op module
fully loaded (emmalloc wasm + closured glue) is about 12.7 KB + 18 KB raw, and
roughly 6 KB + 7.5 KB gzipped, so on the order of 13-14 KB gzipped over the
wire for the first operator.

Marginal cost per additional operator. Measured by comparing the one-op build
(17,459) to a multi build (18,836) that adds two distinct subclass types
reusing the kernel plus one truly distinct kernel (`RollingSum`) plus its batch
function:

```
one_Oz.wasm   = 17,459
multi_Oz.wasm = 18,836
delta         =  1,377 bytes  for 3 extra classes + 1 extra free function
```

That is roughly 340-460 bytes of raw wasm per added operator class, glue
included. The two subclass types isolate almost pure Embind registration glue
(constructor invoker, two method invokers, the JS-visible name string) because
they share RollingMean's `append` body, which the toolchain deduplicates. The
distinct `RollingSum` adds glue plus its own small kernel body. Gzip compresses
this well, since the registration glue is highly repetitive across operators.

What dominates the size. Not the kernels. The first operator's ~17.5 KB (or
~12.7 KB with emmalloc) is almost entirely the Emscripten runtime plus the
Embind support machinery: the type-registration system, `std::string` binding,
`memory_view` binding, malloc/free, and exception glue. The template kernels
themselves are tiny (a rolling mean is a handful of arithmetic ops over a ring
buffer). So the cost model is a large fixed baseline plus a small, compressible
per-operator increment.

Honest projection for ~230 operators in one monolithic module:

- Raw wasm: ~12.7 KB baseline + 230 x ~0.4 KB is about 12.7 + 92, call it
  ~105 KB, but real operators vary. The heavy ones (polynomial regression,
  order-statistic medians, spectral filters) pull in more of the standard
  library (`<vector>` growth paths, sorting, `std::complex`, math), so a
  realistic band is ~120-220 KB raw.
- Gzipped: the glue is repetitive, so gzip ratio improves as operator count
  grows. Expect roughly ~45-80 KB gzipped for all 230 in one module.
- JS glue stays roughly fixed (~18 KB closured, ~7.5 KB gzipped) regardless of
  operator count, since it is runtime, not per-operator.

So an all-ops monolithic module lands around 130-230 KB raw and 55-90 KB
gzipped over the wire. That is entirely shippable for a web library. Levers, in
order of impact:

1. `-sMALLOC=emmalloc` (~27% off the wasm baseline, applies once).
2. `--closure=1` on the JS glue (more than halves it, applies once).
3. `-Oz` over `-O2` (about 6% off the wasm).
4. `-sFILESYSTEM=0` (already applied here; strips the FS runtime).
5. Curated subsets or per-op / per-family modules with lazy loading, so a page
   downloads only the operators it uses. This is the big structural lever if
   the monolith ever feels heavy: split by topic (rolling, microstructure,
   Ehlers, ...) and load on demand.
6. Dead-strip and exception settings (`-fignore-exceptions` is already in
   effect via the toolchain defaults) to trim unwind glue.

Binary size is not the blocker the brief worried it might be. The baseline is
paid once and each operator is cheap.

## Top gotchas encountered

1. Embind keys class registrations by C++ `type_id`, not by the JS name.
   Registering the same C++ type under two names aborts at module load with
   "Cannot register type ... twice". The first attempt registered RollingMean
   under alias names and failed. Each operator exposed to JS must be a distinct
   C++ type. This is fine for screamer (230 distinct operator classes) but it
   rules out cheap name-aliasing, and it means the marginal-cost measurement
   had to use distinct subclass types.

2. Heap views go stale under memory growth. With `-sALLOW_MEMORY_GROWTH=1`, a
   `Float64Array` over the heap (whether `HEAPF64` or a `typed_memory_view`) is
   detached when the heap grows, and any later allocation can trigger growth.
   Every heap read/write must use a view fetched after the most recent
   allocation. Caching a view across a malloc is a use-after-free waiting to
   happen. The driver re-fetches `viewF64` each time for this reason.

3. `HEAPF64` is not on the module by default under a minimal build.
   `-sFILESYSTEM=0` and the default export set do not expose the heap typed
   arrays as `Module.HEAPF64`, so the first batch attempt hit
   "Cannot read properties of undefined". Rather than add
   `-sEXPORTED_RUNTIME_METHODS`, the cleaner fix was to marshal through a small
   Embind `typed_memory_view` helper (`viewF64`) for both reads and writes,
   which keeps the heap access on the C++ side and avoids the stale-global
   problem too.

Runners-up: the standalone `wasm-opt` needing `--all-features`; and
`-sMODULARIZE -sEXPORT_ES6=1` giving a default export that is an async factory
(`const mod = await factory()`), not the module itself.

## Closing verdict and the real engineering work

A screamer WASM binding is feasible. The kernels are already WASM-clean (pure
C++, no threads, RTTI, SIMD intrinsics, Eigen, or Boost, as the project
requires), and this spike ran one end to end with exact numerical parity to
Python. The three feature mappings the Python API is built on all have clean
WASM equivalents, and async streaming is actually simpler in JS.

The real work is not in WASM. It is the same base-class split the nanobind
migration and the WASM direction both want:

1. Decouple the operator base classes from nanobind. Today
   `include/screamer/common/base.h` (`ScreamerBase`) and `functor_base.h`
   (`FunctorBase`) include `<nanobind/nanobind.h>`, and every public operator
   header includes `base.h`. So `screamer/rolling_mean.h` cannot compile
   without CPython, which is why this spike had to wrap `detail/rolling_mean.h`
   directly instead of the public op. The fix is to push all binding-specific
   code (ndarray marshalling, dispatch) out of the base classes into a
   nanobind-only layer, leaving the operator headers depending only on pure
   compute contracts. The `detail/` kernels already are pure; the base classes
   are the coupling point.

2. Add an Embind dispatch layer parallel to the nanobind one. Once operators
   depend on a pure base, write an Embind adapter that gives each operator the
   scalar/batch/lazy dispatch this spike prototyped in `spike.cpp` and
   `driver.mjs`. This is mechanical and can be code-generated per operator the
   same way the nanobind bindings are, since all operators share the
   `append`/`reset` contract.

3. Apply the binary-size strategy: emmalloc, closure, `-Oz`, `-sFILESYSTEM=0`,
   and a module-splitting plan (per-family or curated subsets with lazy load)
   held in reserve for when the monolith grows.

Open risks:

- Operators that reach further into the standard library (sorting, order
  statistics, `std::complex`, larger `<vector>` churn) will cost more per op
  than RollingMean; the ~0.4 KB marginal is a floor, not an average. A second
  measurement over a heavy operator would tighten the 230-op projection.
- Exception handling. The kernels throw `std::invalid_argument` on bad config.
  This spike relied on default Embind exception behavior and did not exercise a
  throw across the boundary; a production binding needs a decided error mapping
  (Embind can surface C++ exceptions as JS exceptions, at some size cost) and a
  test for it.
- Memory-ownership ergonomics. The manual `malloc`/`freeBuf` and `.delete()`
  discipline is correct but easy to get wrong in user code. A production
  binding should hide it behind wrapper objects with clear lifetimes (the
  factory in `driver.mjs` is a start), and consider `FinalizationRegistry` as a
  safety net, not a primary mechanism.
- The base-class refactor is shared with the nanobind work and must not
  regress the Python path; it should land behind the existing test suite with
  Python parity held throughout.
