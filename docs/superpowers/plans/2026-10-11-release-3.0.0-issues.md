# Release 3.0.0 Issues Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement every item of the 3.0.0 tracker whose status is "to implement" or "to do", so that every row can be marked `done (commit)`.

**Architecture:** Each task closes one tracker row (a few close two closely related rows). Logic moves to the shared C++ core wherever the decision says so (B2, B3, B4, D2), and both bindings (Python via nanobind, JS via Embind/WASM plus the generated TypeScript) are thin layers over it. Behavior that changes for working 2.8.0 code is listed in the CHANGELOG under "Changed" or "Fixed" and checked with the compat gate.

**Tech Stack:** C++17 headers (`include/screamer`), nanobind bindings (`bindings/`), Emscripten/Embind (`wasm/`), TypeScript (`js/src`, generated `js/src/generated/ops.ts` from `devtools/wasm/gen_ts_api.py`), pytest, `node --test` with tsx.

**Spec:** `docs/superpowers/release-3.0.0-issues.md`, the tracker. The decision text in each row's Status column is binding. The six rules and stream-state rule D8 are in `docs/polymorphic_api.md` ("The six rules") and `docs/streaming.md`.

## Global Constraints

- Branch `feat/shape-contract`. Never push, never merge, never run `make patch/minor/major`, and never edit version strings.
- All operator logic lives in C++. Python and JS contain only argument adaptation, labels, and the binding's native types. Where possible, move functionality to the shared C++ base (user rule, B2).
- Python and JS parity is a hard default: every behavior added in one language is added in the other, in the same task, unless the task says otherwise.
- After any C++ change: `make install-dev` (not just `make build`). Python tests: `.venv/bin/python -m pytest -q -x -p no:cacheprovider` (the full suite runs about 10k tests). JS: `cd js && npm run build:wasm && npm run build && npm test`.
- Compat gate: `.venv/bin/python devtools/compat_probe.py --diff` must show only rows that the tracker decided to change. Paste any new row into the task report.
- Docs and CHANGELOG prose: no em-dashes, plain language, lead with the point (`feedback_writing_style`). Docs must build: `make -C docs html` with no new warnings.
- Error classes: Python raises `ValueError` for shape or count mismatches and `TypeError` for wrong kinds. JS raises `RangeError` for shape or count mismatches and `TypeError` for wrong kinds (A4).
- Each task adds its CHANGELOG entry under `Unreleased` in the right section (Added / Changed / Fixed). Each task marks its tracker row `done (<short sha>)` in the same commit as the code, or in a follow-up commit if the sha is needed.
- Commit messages end with:

## Review Focus

1. A long-running process that creates and drops many streams, live sessions and pipelines must not grow in memory (C5 soak). Pinned in Task 11.
2. Malformed or user-mutated JS input (a bad `NdArray`, a mutated parameter array, a user iterator that throws a number) must never reach C++ memory unchecked or change an existing operator. Pinned in Tasks 2, 3, 4.
3. 1-D inputs must give bit-identical results to 2.8.0 after every refactor of a shared path (D1, D2, C2, B2, B4). Pinned by the compat gate in each of those tasks and in Task 29.
4. Batch must equal stream bit for bit after D4 and C6 on every operator. Pinned by the existing contract suites (`tests/test_shape_contract.py`, `js/test/streaming_contract.test.ts`), which Task 13 and Task 14 must run in full.
5. A speed change on any operator must be visible: the benchmark gate of Task 13 compares all ~218 operators against the current numbers.
